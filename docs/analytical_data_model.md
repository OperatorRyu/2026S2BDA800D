Analytical Data Model
1. Purpose

This document defines the analytical data model for the Synthea FHIR healthcare dataset used in the Big Data Analytics 800 group project.

The source dataset consists of FHIR JSON bundles containing approximately 8.9 million healthcare resources across 129,218 patient records.

The purpose of the analytical model is to transform the source FHIR data into a set of structured, queryable datasets suitable for:

    Descriptive analytics

    Diagnostic analytics

    Predictive modelling

    Statistical analysis

    Data visualisation

    Machine learning

    Large-scale processing using technologies such as Apache Spark

The analytical model deliberately separates the original FHIR representation from the structures used for analysis. The source JSON files remain the raw, immutable dataset, while the analytical layer provides normalized and analysis-friendly representations.

4. Core Analytical Entities
4.1 Patient

The Patient entity represents an individual synthetic patient.
Proposed columns
Column	Type	Description
patient_id	string	Unique patient identifier
gender	string	Patient gender
birth_date	date	Patient date of birth
marital_status	string	Marital status where available
race	string	Race classification
ethnicity	string	Ethnicity classification
birth_city	string	City of birth
birth_state	string	State of birth

The raw FHIR Patient resource contains additional fields. Only fields required for analysis should be promoted into the analytical model.
Primary key

15. Analytical Grain

Each analytical table has a defined grain.
Dataset	Grain
Patient	One row per patient
Encounter	One row per encounter
Condition	One row per condition
Observation	One row per observation/component
DiagnosticReport	One row per diagnostic report
Procedure	One row per procedure
MedicationRequest	One row per medication request
Immunization	One row per immunization
CarePlan	One row per care plan
AllergyIntolerance	One row per allergy record

Defining grain explicitly prevents accidental duplication during joins and aggregation.
16. Storage Format

The extracted analytical datasets should be stored in Apache Parquet format.

Proposed structure:

data/
├── raw/
│   └── fhir/
│
└── processed/
    └── parquet/
        ├── patient/
        ├── encounter/
        ├── condition/
        ├── observation/
        ├── diagnostic_report/
        ├── procedure/
        ├── medication_request/
        ├── immunization/
        ├── care_plan/
        └── allergy_intolerance/

Parquet is preferred because it provides:

    Columnar storage

    Compression

    Efficient analytical reads

    Schema information

    Compatibility with Apache Spark

    Efficient selection of only required columns

17. Partitioning Strategy

Large datasets should be partitioned where doing so improves query performance.

Candidate partitioning columns include:

year
month

for time-oriented clinical resources.

For example:

observation/
├── year=2019/
├── year=2020/
├── year=2021/
└── ...

Partitioning should be validated against actual query patterns rather than applied indiscriminately.

Patient identifiers should not be used as high-cardinality partition columns.

19. Data Quality Requirements

The extraction pipeline must preserve the distinction between missing data and invalid data.

Validation should include:
Structural validation

    Valid JSON

    Expected FHIR resource structure

    Expected resource types

    Required identifiers

Type validation

    Dates must be parseable

    Numeric observations must be numeric where applicable

    Boolean fields must contain valid boolean representations

Completeness validation

Track null/missing values for analytical fields.
Duplicate validation

Detect duplicate resource identifiers.
Referential integrity

Validate relationships between:

Patient
Encounter
Condition
Observation
DiagnosticReport
Procedure
MedicationRequest
Immunization
CarePlan
AllergyIntolerance

The reconnaissance stage established that the currently observed references resolve successfully.

The model supports several potential research questions.
Descriptive analytics

Examples include:

    Patient demographics

    Encounter volumes over time

    Most frequently recorded conditions

    Medication utilization

    Procedure frequencies

    Immunization patterns

    Observation distributions

Diagnostic analytics

Examples include:

    Conditions associated with increased healthcare encounters

    Relationships between diagnoses and procedures

    Relationships between conditions and medications

    Patterns in diagnostic testing

Predictive analytics

Potential models could investigate:

    Predicting future encounters

    Predicting the presence of selected conditions

    Predicting medication usage

    Patient risk classification

Any predictive analysis must clearly define the prediction target, observation window, and avoidance of information leakage.
Prescriptive analytics

The project may use analytical findings to discuss potential process improvements or healthcare resource allocation scenarios. Because this is synthetic data, such recommendations should be presented as analytical scenarios rather than clinical guidance.
21. Big Data Characteristics

The dataset provides opportunities to demonstrate the five commonly discussed Big Data characteristics.
Characteristic	Dataset relevance
Volume	8.9 million FHIR resources and approximately 13 GB of raw JSON
Variety	Multiple FHIR resource types and nested/semi-structured JSON structures
Velocity	Temporal healthcare events can be analysed as event streams, although the Kaggle dataset itself is a static snapshot
Veracity	Data validation, schema checks, missing-value analysis and reference-integrity testing are required
Value	The dataset can support healthcare utilization, disease, medication and clinical-event analysis

Velocity should be described carefully: the supplied Kaggle dataset is static, so the project demonstrates temporal/event-oriented data rather than a live streaming ingestion system.
22. Design Principles

The analytical model follows these principles:

    Preserve the raw data. Raw FHIR JSON must remain immutable.

    Do not flatten everything blindly. FHIR is hierarchical and different resources require different extraction strategies.

    Define analytical grain explicitly.

    Preserve relationships between resources.

    Separate extraction from analysis.

    Validate before publishing analytical datasets.

    Prefer reproducible transformations.

    Use columnar storage for analytical workloads.

    Keep the pipeline scalable enough to process the complete dataset.

    Document assumptions and transformations.
